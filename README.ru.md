# OpenWrt WiFi Guard

Лёгкий монитор Wi-Fi-клиентов для OpenWrt. Реализована **фаза A**: динамическое обнаружение `hostapd.*`, подписка на успешные авторизации, сверка подключений, постоянный реестр и структурированный лог `new_device`. Ethernet-клиенты не отслеживаются.

**Пока не реализованы:** доставка в Telegram, LuCI, UCI, procd и `.ipk`. Этапы — в [PLAN.md](PLAN.md). Программа не открывает сетевые порты и никого не блокирует.

## Сборка и проверки

Нужны Go 1.23+ и Make; сторонних Go-зависимостей нет. Python 3 требуется только для smoke-теста на компьютере, не на роутере.

```sh
make check
make build arm64
make smoke
```

Результаты: `build/wifi-guard` и `build/wifi-guard-linux-arm64`. ARM64-сборка не заменяет проверку на AX3000T/OpenWrt 24.10.2. Официальные пакеты под `aarch64_cortex-a53` появятся на этапе D.

## Ручной SSH-тест без установки

Укажите **настоящий адрес** своего роутера с уже настроенным SSH-доступом:

```sh
export ROUTER='root@YOUR_ROUTER_ADDRESS'
ssh "$ROUTER" 'ubus list "hostapd.*"'
ssh "$ROUTER" 'ubus call hostapd.YOUR_AP_OBJECT get_clients'
scp -O build/wifi-guard-linux-arm64 "$ROUTER":/tmp/wifi-guard
ssh -t "$ROUTER" 'chmod 700 /tmp/wifi-guard; /tmp/wifi-guard -state /tmp/wifi-guard-test/state.json -reconcile 60s -flush 10s'
```

Подставьте имя AP из вывода первой команды. `scp -O` нужен для OpenWrt без SFTP; при работающем SFTP его можно опустить.

1. Уже подключённые устройства должны импортироваться **без** `new_device`.
2. Устройство с ранее неизвестным тестовым MAC должно дать ровно одну запись после авторизации.
3. Повторное подключение и переход между диапазонами не должны создавать новые уведомления.
4. `probe`, `auth`, `assoc` не должны добавлять устройства.
5. Ctrl-C завершает процесс с сохранением состояния. Повторный запуск с тем же файлом не должен повторять обнаружение.
6. Перезапуск Wi-Fi проверяйте только в согласованное окно: программа должна восстановить подписку и сверить клиентов.

```sh
ssh "$ROUTER" '/tmp/wifi-guard -state /tmp/wifi-guard-test/state.json -dump'
```

`/tmp` не переживает перезагрузку роутера. После аппаратной проверки и согласования можно использовать постоянный путь `/etc/wifi-guard/state.json` (по умолчанию). Каталог создаётся с правами 0700, файл — 0600. Существующий путь должен принадлежать пользователю процесса; каталог с записью для group/other, файл с доступом для group/other и symlink не допускаются. Используйте отдельный защищённый подкаталог, не файл прямо в общей `/tmp`. UCI, firewall и службы программа не изменяет. Одновременно запускайте только один экземпляр на файл состояния.

## Параметры

- `-ubus ubus` — путь к исполняемому файлу, без shell-интерполяции.
- `-state /etc/wifi-guard/state.json` — реестр и история.
- `-bootstrap import` — тихий первоначальный импорт; `notify` регистрирует начальных клиентов как новых. Это не сбрасывает ранее сохранённые устройства.
- `-reconcile 60s` — повторное обнаружение AP и сверка клиентов.
- `-retry 5s` — восстановление подписки и незавершённого начального импорта.
- `-resubscribe 5m` — профилактическая переподписка при неизменных именах AP; необходимость проверяется при сверке клиентов.
- `-command-timeout 5s` — таймаут каждой отдельной команды list/call, но не простаивающей подписки.
- `-flush 30s` — период записи изменений реестра/подключений.
- `-checkpoint 15m` — более редкое сохранение изменений только `last_seen`; SIGINT/SIGTERM сохраняют оба типа.
- `-history-limit 500` — предел истории, допустимо 1–10000.
- `-dump` — показать сохранённый JSON без ubus и сетевых запросов.

Первое окно импорта ограничено первой попыткой снимков: накопленные за это время события импортируются без сообщений. Отказ одной AP не подавляет последующие живые авторизации; беззвучным остаётся только её первый успешный снимок. Список ожидающих первоначального снимка AP сохраняется между запусками. Отличить новое устройство от старого внутри начального окна достоверно невозможно.

## Ограничения и безопасность

`new_device` пока означает запись в лог, **не сообщение Telegram**. Неизвестные IP, hostname, SSID и диапазон не выдумываются. Известное устройство сохраняется с доверием `unknown`: «известное» не равно «доверенное». Изменение имени/доверия появится вместе с защищённым LuCI/RPC.

MAC не является надёжной аутентификацией: его рандомизация может выглядеть как новое устройство. Блокировок нет. Ethernet, DHCP/ARP и устройства, только посылающие probe, не учитываются.

Запись атомарная с fsync, но пакетная ради ресурса flash: внезапное отключение питания/SIGKILL до очередной записи может потерять последние наблюдения. Повреждённый файл не сбрасывается автоматически, а останавливает запуск. При ошибке записи грязное состояние остаётся в памяти и повторно сохраняется; ошибка финальной записи даёт ненулевой код выхода. Делайте резервные копии.

История ограничена, реестр известных MAC сохраняется целиком; следите за размером flash. Чтение и запись ограничены 16 МиБ. Превышение лимита не заменяет старый рабочий файл; автоматического удаления известных MAC нет. При исчерпании ёмкости требуется решение оператора, а свежие изменения остаются только в памяти до успешного сохранения. Логи и реестр содержат идентификаторы устройств — не публикуйте их. Локальный `AGENTS.md` сохранён, но исключён из git из-за наблюдавшегося MAC.

При `no_access_points` проверьте `ubus list 'hostapd.*'`; повторы продолжаются. `reconcile_failed` не переводит клиентов недоступной AP в offline: состояние может оставаться устаревшим до восстановления. `subscription_failed` приводит к переподписке; мусорные JSON-строки игнорируются. При `state_save_failed` проверьте место и права. Полный список ограничений и архитектура: [README.md](README.md), [docs/architecture.md](docs/architecture.md).

## Удаление

Остановите ручной процесс; при необходимости удалите тестовый бинарник и состояние из `/tmp`. Постоянный реестр удаляйте только если хотите забыть устройства. Пакеты, службы, UCI и firewall на этом этапе не устанавливаются и не меняются.
